## What is changed

The script uninstalls the image's `mooncake-transfer-engine-cuda13` 0.3.13 and installs the public EFA
build of the same Mooncake release line, `mooncake-transfer-engine-efa-cuda13==0.3.13.post1`, from PyPI
with `--no-deps`. Both packages provide the same `mooncake` Python module; the EFA build adds the AWS EFA
(libfabric) transport. The commands are the ones in SGLang's documentation.

Nothing else changes. No SGLang, Dynamo, or Mooncake source is patched, no forked or rebuilt wheel is
installed, and no other package is added or removed. Mooncake only moves KV-cache pages from prefill to
decode workers; it performs no model computation, so the change cannot alter model numerics.

## Why the unmodified upstream image cannot run this benchmark

The B300 DSXE nodes connect to each other over AWS EFA; they have no InfiniBand fabric. The image's
standard `mooncake-transfer-engine-cuda13` build does not include the EFA transport, so the disaggregated
recipes cannot transfer KV cache between the prefill and decode nodes with it. SGLang's PD-disaggregation
documentation prescribes replacing the standard CUDA 13 Mooncake package with the EFA build on AWS EFA
instances, using these exact commands, and the recipes set `MOONCAKE_PROTOCOL=efa` as that documentation
describes.

## Removal plan

Retire `install-mooncake-efa-cu13.sh` once an upstream `lmsysorg/sglang` image ships an EFA-capable
Mooncake build. At that point, bump the pinned `image:` for `dsv4-fp4-b300-dynamo-sglang-agentic-disagg`
to that image, remove the `setup_script` lines from the three disaggregated recipes, delete the script,
and delete this waiver in the same PR.
