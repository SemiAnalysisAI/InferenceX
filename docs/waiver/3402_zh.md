## 补丁内容

SGLang 的 `HiCacheController` 和 `HybridCacheController` direct load-back 路径，
把索引就绪等待及原有逐层复制提交交给一个绑定设备的 FIFO 线程。调度器在等待 CUDA 工作前
拿到 producer ID。原有 consumer 边界会等待 load event 完成记录；复制完成仍由设备事件控制。
Producer slot 复用、reset 排空和错误传播保留必要的顺序。提交失败会直接报错，不会生成成功 ack。
非 direct 后端保留原有索引复制与事件记录顺序。

安装器只接受 revision `211ee642` 的两份精确源码哈希，或两份精确的已打补丁哈希。
未知或混合状态会在引擎启动前失败。镜像、拓扑、HiCache 容量/后端/策略、watchdog、
工作负载、golden acceptance 和 draft 精度保持不变。

## 未修改镜像在本次测试中的失败原因

[Run 35925853577、attempt 1、job 107401191650](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/35925853577/job/107401191650)
触发了 300 秒 scheduler watchdog。保留的 prefill 栈显示 DP3 位于 HiCache direct load-back
的 `device_indices.cpu()`，DP0/1/2 在等待 DP-attention batch all-gather。
源码 `211ee642` 在构造 batch 时、进入该 collective 之前执行这次索引复制。
因此，阻塞式 device-to-host 复制可能使一个 rank 无法进入下一次 host collective。

这是已观察到的失败路径及候选同步循环机制，不表示原镜像每次执行都会失败；历史运行曾通过。
更早的 kernel 或 driver 故障也可能产生相同调用栈。只有完成精确运行环境的复现验证，
才能把原因或修复报告为已确认。
