## What is patched

The paired [Dynamo and SGLang patches](../../benchmarks/multi_node/srt-slurm-recipes/configs/glm52-b200-c48/README.md)
target Dynamo `c3e05f0244ae6264d7953f68e2499c6dc2f54723` and SGLang
`0084030179bfba86bfeb6d43f7997d4076329d2c`. Dynamo's native prefill router propagates
late prefill failures to the original request; its Python handlers recognize
streaming abort responses and order cancellation after known request registration
and dispatch. SGLang quarantines failed-transfer buffers until the actual owned
workers exit. Local `srun` exit alone does not permit release or resource reuse.

The launcher adds an 1800-second request failure budget, not a proven latency
bound. Its [cleanup watcher](../../runners/watch_glm52_b200_c48_cleanup.py) verifies
exact job/user/runner/output identity, allows 300 seconds after authoritative
failure or cleanup, and cancels only that job if workers remain. Isolated scored
request errors do not trigger this guard or change acceptance thresholds.

The [installer and manifest](../../benchmarks/multi_node/srt-slurm-recipes/configs/glm52-b200-c48/)
check original source/absence and native binary identities, then installed outputs.
The sealed pair uses build-receipt SHA-256
`27aa9a6eb223616d956dd7d507c0e26839cadcfb84339179898ff3a502ccbcba`.
The source, dependency locks, versions and release features remain pinned; the
reviewed patch is the intended source delta. Its native wheel is truthfully
`cp310-abi3-manylinux_2_39_x86_64`, with no `manylinux_2_28` or broader portability
claim. The Python/native wheel hashes and build procedure are in the linked README.

## Why the unmodified image failed this benchmark

[Run 36188119567, job 108246573370](https://github.com/SemiAnalysisAI/InferenceX/actions/runs/36188119567/job/108246573370)
stalled at 49/51 initial warmup requests and reached the four-hour allocation
limit without a scored window. Saved prefill logs show `NIXL_ERR_REMOTE_DISCONNECT`;
the initiating disconnect and an independent DP7 stall remain unexplained.
Exact-source checks found swallowed Python abort responses, discarded native
bootstrap-tail errors and cancellation waiting for a first-output request ID.
These justify failure containment, not a claim that containment repairs the
initiating fault or makes the benchmark pass.

## Removal plan

Validate a suitable unpatched upstream image on the same C48 workload and the
failure/cancellation/transfer-teardown lifecycle, preserving full-window required
PowerX and all acceptance criteria. Then remove the paired runtime/Python patches,
sealed-payload setup, role gates, containment-specific deadline/cleanup selection
and this waiver in the image-update PR. Retain historical failures. If the
candidate fails, diagnose that evidence before further recovery; do not extend
the allocation or relax power or scoring acceptance.
